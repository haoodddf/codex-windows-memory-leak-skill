# Windows Codex 内存泄漏规避

核心做法：保留链接目标数据，把 `%APPDATA%\Codex\web\Codex` 的目录链接替换成内容一致的普通目录，减少经该链接访问文件的路径。作者在自己的机器上确认问题已解决；这是特定环境的规避方案，不是对所有 Codex 内存问题的修复保证。

作者环境（2026-10-08 实读）：Windows 11 家庭版 中文版 26H2，64 位，OS 构建 **26300.9457**；Codex 商店包 **26.1002.7124.0**。这些是制作时的环境，不应当作通用版本限制；完整记录见 [诊断与证据](references/diagnosis.md)。

历史环境（作者反馈）：此前使用 **Windows 11 25H2** 时也出现过同类问题。当时的完整构建号、驱动及 Codex 版本未知，本次未单独复测 25H2 上的修复效果。

## 先判断是否适用

1. 区分 **系统非分页池持续增长** 与 Codex 进程工作集/私有内存增长。关闭窗口未恢复内存可作为线索，不能单独证明内核泄漏。记录 Windows、Codex MSIX 版本和内存趋势，详见 [诊断与证据](references/diagnosis.md)。
2. 在 Windows PowerShell 5.1 或 PowerShell 7 运行本 skill 的 `scripts/repair-codex-web-link.ps1 -Action Inspect`。默认只检查路径、目录链接和已安装包，不修改数据。脚本路径相对于本 skill 目录。
3. 只对已确认的 Windows MSIX Codex、存在且可读取的 Junction/SymbolicLink 数据目录考虑转换。该路径或父目录不存在、已经是普通目录、链接目标不清楚、父目录或数据内部还有 reparse point 时，不强行修复；报告检查结果并停止转换。
4. 如果用户说已经解决，只核查现状、整理方案或协助验证；不要重新修复，也不要重建链接。CLI、WSL、macOS 和普通进程内存增长需要另行诊断。

## 执行转换

先读 [操作与恢复](references/operation.md)，使用其中与当前脚本接口一致的命令。

- 用户明确要求修复才执行转换；仅制作 skill、解释截图或检查状态，不授权修改浏览器数据。已有明确修复授权无需重复确认。
- **完全退出 Codex，然后从 Windows 开始菜单打开独立 PowerShell 执行**。不要从仍在运行的 Codex 集成终端或代理工具中执行 Convert/Rollback，也不要脚本内强杀应用。将具体命令准备好交给用户在退出后运行。
- 先 `-Action Convert -WhatIf`，再执行 Convert。脚本保留原链接和原目标，使用邻接普通目录暂存副本并逐文件核对内容，随后替换路径；遇到校验失败或不安全路径立即停止。
- 不删除源目标，不递归删除任何链接，不移动整个 AppData，不更改 `.codex` 配置或认证，不禁用驱动、服务、安全软件，也不修改或重装 MSIX/WindowsApps。
- 有错误时检查本次脚本报告的路径与状态；不要自行覆盖备份或重复猜测修复。只对已确认的本次备份执行恢复。

## 验证与回滚

转换完成先确认路径是普通目录、复制校验通过、备份信息已保存。重新打开 Codex，验证浏览器/页面、登录及常用功能能正常使用。

内核池泄漏可能需要 Windows **重启** 才释放已累积内存。先让用户保存工作；不自动重启。使用“重启”建立新基线，快速启动开启时的关机再开机不等价。按 [诊断与证据](references/diagnosis.md) 比较相同负载下重启前后/修复前后的增长趋势；如果没有修复前采样，只报告修复后观察结果和用户历史反馈。

若功能异常，完全退出 Codex，在独立 PowerShell 使用脚本的 Rollback。恢复会保留修复后的普通目录，恢复原链接；修复后新增的浏览器数据不会自动合并到旧目标，需按实际需要处理冲突。不要承诺“无损合并”。

完成时区分：路径修复结果、功能验证、内存趋势验证、用户实测结论。缺少任何一项就说明未验证。更新或重新安装后若症状复发，重新 Inspect；不要预设更新必然重建链接。
